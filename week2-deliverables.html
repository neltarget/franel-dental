1. Product Requirements Document

What we are building, for whom, and how we will know it works

1.1 Product Vision

Franel is a patient-conversion AI Agent that lives on WhatsApp and helps private dental clinics turn enquiries into booked, confirmed, and attended appointments. It answers questions, qualifies leads, checks calendar availability, books appointments, follows up with patients, and escalates to human staff when needed.

The eventual goal is a multi-tenant platform where Franel's core personality stays constant and only the clinic-specific configuration changes. Each clinic gets its own isolated environment: its own calendar, its own patient data, its own dashboard, and its own conversation history.

1.2 Product Goals

  1. Prove that Franel can convert enquiries into bookings. The core question for the POC is simple: can a patient WhatsApp the clinic, have a natural conversation, and end up with a real appointment on the calendar?
  2. Reduce missed enquiries. Staff are stretched thin. Messages go unanswered. Follow-up doesn't happen. Franel fills these gaps without adding workload.
  3. Recover lost leads. People who enquire but don't book are currently abandoned. Franel follows up systematically and respectfully.
  4. Free up staff time. Receptionists spend hours answering the same questions. Franel handles the repetitive work so staff can focus on patients in front of them.
  5. Build toward a scalable product. The POC is one clinic. The architecture should support multiple clinics from the start.

1.3 Target Users

Clinic Owner The practice owner or decision maker Fewer missed enquiries, fewer no-shows, visibility into what's happening, and confidence that the AI is accurate

1.5 Functional Requirements

Conversation

  • Understand natural Ghanaian English input
  • Handle multiple intents in one message
  • Answer before qualifying
  • One question at a time during qualification
  • Never repeat questions already answered
  • Use WhatsApp-native formatting (bold, italic)

Booking

  • Check real-time calendar availability
  • Offer a small number of valid slots
  • Re-validate slot before creating appointment
  • Confirm only after tool success
  • Handle rescheduling and cancellation
  • Never create duplicate events

Follow-up

  • Non-booker follow-up at configurable intervals
  • Appointment reminder (default: 24 hours before)
  • No-show recovery (same day or next available)
  • Check patient state before sending any scheduled message
  • Stop when patient asks, books, declines, or is handed to human

Escalation

  • Tier 1: immediate emergency guidance + staff alert
  • Tier 2: urgent, route to earliest appointment
  • Tier 3: operational (complaint, human request, policy exception)
  • Preserve conversation context for the human
  • Continue monitoring after handoff where permitted

Attendance

  • Post-appointment check-in via WhatsApp (configurable timing, default: appointment end + 1 hour)
  • Patient self-reports attendance by replying YES or NO
  • Staff can manually mark attendance from admin dashboard
  • Attendance states: pending, attended, no-show, cancelled
  • 24-hour flag timeout: unanswered check-ins flagged for staff review
  • On no-show, offer rescheduling automatically
  • Attendance metrics displayed in dashboard (attended count, no-show count)
  • Attendance tracked per appointment in Supabase with marked_by and marked_at fields

1.6 Non-Functional Requirements

Performance

  • First response under 3 seconds for standard messages
  • Calendar check under 2 seconds
  • Booking confirmation under 5 seconds
  • Dashboard loads under 2 seconds

Reliability

  • Never claim a booking without tool confirmation
  • Never invent prices, times, or policies
  • Graceful handling of tool failures with patient notification
  • State persistence across conversation turns

Security

  • Per-clinic data isolation. No cross-clinic data sharing
  • Conversation logs retained for 90 days, then purged
  • No exposure of internal state, tool names, or escalation logic to patients
  • Encryption at rest for patient data

Usability

  • WhatsApp-native experience. No learning curve for patients
  • Dashboard accessible via web browser, no install required
  • Escalation visible and actionable for staff within 1 click

1.7 Constraints and Assumptions

WhatsApp 24-hour window (production constraint)

The official WhatsApp Business API has a customer service window. When a patient initiates a conversation, free-form responses are possible within 24 hours. Outside that window, business-initiated outbound messages require approved templates.

For the POC, we use Baileys (unofficial WhatsApp connection) which does not have this restriction. But the follow-up system must be designed with this constraint in mind for production. Specifically:

  • Follow-up messages within 24 hours of last patient message: free-form, no restriction
  • Follow-up messages after 24 hours: must use pre-approved WhatsApp message templates
  • The follow-up module should track the timestamp of the last patient message and route accordingly
  • Template message support should be built as an adapter, not hardcoded, so the POC can work without it and production can plug it in

Other constraints

  • POC scope: One clinic, one WhatsApp number, one Google Calendar. Multi-tenant architecture is designed but not fully implemented in POC.
  • No clinical advice: Franel never diagnoses, prescribes, or promises clinical outcomes. This is a hard boundary.
  • Clinic-approved content only: All service information, pricing, and policies come from the clinic knowledge source. Franel never invents facts.
  • Voice and image support: Voice messages are transcribed to text before processing. Images are received and acknowledged but not clinically analyzed.

2. User Journey

From first message to attended appointment

The primary journey is a straight path from enquiry to appointment. But real conversations don't always go in a straight line. Below is the happy path, followed by the edge cases Franel must handle.

Happy path: enquiry to appointment

1

Patient sends first message

Patient WhatsApps the clinic, usually from a social media ad or referral. Message might be "how much is teeth whitening" or "I want to book an appointment" or just "hello."

↓
2

Franel greets and identifies intent

Franel responds with a warm greeting and reads the message to understand what the patient wants. If the intent is clear (pricing, booking, service info), Franel addresses it immediately. No cold questionnaire.

↓
3

Franel answers the question

Using verified clinic information, Franel provides the answer. Pricing is stated clearly. Services are explained. If something varies (like final cost after assessment), Franel says so honestly.

↓
4

Franel qualifies naturally

If the patient shows interest, Franel asks one useful question at a time to understand the need, timing, and any constraints. This is conversation, not interrogation. If the patient is clearly ready, Franel skips ahead to booking.

↓
5

Franel offers appointment slots

Franel checks the clinic's Google Calendar for real availability and offers a small number of valid options. "I have Tuesday at 10:00 am and Wednesday at 2:30 pm. Which works better?"

↓
6

Patient selects a slot

The patient picks a time. Franel re-validates the slot to make sure it's still available, then creates the calendar event.

↓
7

Franel confirms the booking

Only after the calendar tool confirms success, Franel tells the patient the appointment is booked. Confirmation includes date, time, clinic name, and location. "You're booked for Tuesday, 15 September at 10:30 am. I'll remind you before the appointment."

↓
8

Franel sends reminder

Based on clinic-configurable timing (default: 24 hours before), Franel sends a reminder. The reminder checks current state first: if the patient has already cancelled, rescheduled, or asked for no contact, the message is not sent.

↓
9

Patient attends appointment

The patient shows up. The conversion is complete. Lead → Qualified → Booked → Confirmed → Attended.

↓
10

Franel sends post-appointment check-in

After the appointment time passes (configurable, default: appointment end + 1 hour), Franel sends a WhatsApp check-in: "Hi [Name], we hope your visit went well! Could you confirm you attended? Reply YES or NO." If the patient confirms attendance, the status is updated. If the patient reports a no-show, Franel offers rescheduling. If there is no reply within 24 hours, the appointment is flagged for staff review in the dashboard. Staff can also manually mark attendance at any time.

Edge cases

Patient doesn't respond after initial enquiry

Franel follows up based on clinic-configurable intervals (default: 24 hours, 3 days, 7 days). Each follow-up references the original conversation. Stops after 3 attempts, or immediately if the patient books, declines, or asks to stop.

Patient wants to reschedule

Franel identifies the existing appointment, confirms the new preferred time, checks availability, updates the calendar, and confirms the change. Never silently replaces one appointment with another.

Patient cancels

Franel confirms the cancellation, follows clinic policy, and offers to help rebook if appropriate. The slot becomes available for other patients.

No-show

Franel follows up same day or next available day. "Hi Ama, we had an appointment scheduled today. Would you like to reschedule?" Configurable per clinic.

Patient asks for a human

Tier 3 escalation. Franel acknowledges, hands off smoothly, and preserves the conversation context for staff. "I'll flag this for the clinic team so they can assist you directly."

Emergency (Tier 1)

Franel immediately advises the patient to seek emergency care. Does not continue normal conversation flow. Alerts the clinic team. "Facial swelling with difficulty swallowing needs urgent medical attention now."

Clinical question beyond scope

Patient asks "what antibiotics should I take?" Franel declines to prescribe, explains the dentist needs to assess the cause, and offers an appointment. Never invents clinical advice.

Voice message received

Franel transcribes the voice message to text, processes the intent, and responds normally. The patient doesn't need to know the transcription happened.

Image received

Patient sends a photo (e.g., dental card, insurance info, picture of a tooth). Franel acknowledges receipt and asks for relevant context if needed. Does not attempt clinical analysis of images.

Mixed-language input

Patient writes partly in Twi or Ga mixed with English. Franel responds in clear English as usual. If a message is entirely in a language Franel can't interpret confidently, it asks the patient to continue in English.

4. AI Workflow

How Franel processes a message from start to response

A critical design principle guides this workflow: the LLM handles language and conversation, while a deterministic workflow layer handles business logic. Franel does not arbitrarily decide every operation. The conversation and the business rules are separated by design.

4.1 LLM vs Deterministic Workflow

🧠 LLM / Franel handles

  • Language understanding
  • Natural conversation
  • Intent recognition
  • Context from prior messages
  • Choosing the conversational next step
  • Qualification through dialogue
  • Closing patterns
  • Emotional register (warm, calm, professional)

⚙️ Deterministic workflow handles

  • Calendar availability checks
  • Appointment creation and confirmation
  • Lead state transitions
  • Follow-up scheduling
  • Escalation routing
  • Database updates
  • Clinic rule enforcement
  • Reminder timing

Why this separation matters

If the LLM decides when to book, when to follow up, and what state a lead is in, debugging becomes nearly impossible. By separating conversation from business logic, we can test each independently. The LLM can be evaluated on conversation quality. The workflow can be evaluated on booking accuracy. Problems are traceable to a specific layer.

4.3 Intent Classification

Franel classifies incoming messages into intents before acting. A single message can carry multiple intents. When it does, Franel addresses them together in one natural reply rather than forcing separate turns.

Top-level intents

BOOK_APPOINTMENT SERVICE_INFORMATION PRICE_INQUIRY LOCATION OPENING_HOURS URGENT_OR_EMERGENCY RESCHEDULE CANCEL_APPOINTMENT FOLLOW_UP COMPLAINT HUMAN_SUPPORT GENERAL_QUESTION CONFIRM_ATTENDANCE REPORT_NO_SHOW

Service-level intents

TEETH_CLEANING TEETH_WHITENING FILLING EXTRACTION ROOT_CANAL BRACES_OR_ORTHODONTICS DENTAL_IMPLANTS DENTURES CROWNS_OR_BRIDGES PEDIATRIC_DENTISTRY COSMETIC_DENTISTRY TOOTH_PAIN

4.4 Next-Best-Action Priority

At every turn, Franel decides what to do next based on this priority order:

  1. Resolve a Tier 1 emergency signal. If the patient describes symptoms that need immediate care, this comes before everything else.
  2. Answer the patient's actual question. If they asked about price, tell them the price. Don't defer the answer to squeeze in a qualification question.
  3. Resolve a blocker to booking. If something is preventing the patient from booking (unclear pricing, schedule conflict, missing information), address it.
  4. Collect the one missing piece. If only one piece of information stands between the current state and the next step, ask for it.
  5. Offer a relevant appointment. If the patient is ready and qualified, offer available slots.
  6. Complete the booking. If the patient has selected a slot, confirm and create the appointment.
  7. Confirm and prepare. If the appointment is booked, confirm the details and set expectations.
  8. Schedule follow-up. If the patient is interested but not ready, schedule appropriate follow-up.
  9. Escalate. If the situation requires human judgment, escalate at the appropriate tier.

4.5 Qualification Flow

Qualification is treatment-specific, not a universal questionnaire. The questions Franel asks depend on what service the patient is interested in.

Whitening inquiry

  • What does the patient want to achieve?
  • Have they had whitening before?
  • Are they looking for an appointment soon?

Braces inquiry

  • Is this for self or someone else?
  • Child, teen, or adult?
  • Main concern?
  • Interested in consultation?

Tooth pain

  • What symptoms?
  • When did they start?
  • Severe or worsening?
  • Swelling or bleeding?

Child dentistry

  • Age of the child?
  • Specific concern or general check-up?
  • Previous dental visits?
  • Preferred timing?

5.3 POC vs Production

POC Architecture

  • Hermes Agent (core runtime)
  • Baileys WhatsApp bridge (unofficial, no 24-hour window restriction)
  • One dedicated test WhatsApp number
  • Google Calendar (one clinic)
  • Supabase (one clinic database)
  • Admin dashboard (web-based, one clinic view)
  • Closed stakeholder testing

Production Architecture

  • Hermes Agent (core runtime)
  • WhatsApp Cloud API (official Meta integration)
  • Per-clinic WhatsApp numbers
  • Google Calendar (per clinic)
  • Supabase (per clinic database, row-level isolation)
  • Admin dashboard (multi-clinic view)
  • Template message infrastructure (for24-hour window compliance)
  • Follow-up scheduling with state checking

WhatsApp 24-hour window design

For production, the follow-up module must handle the WhatsApp Business API's customer service window. The adapter pattern allows the POC to work with Baileys (no restriction) while the production system plugs in Cloud API template message support without changing the core follow-up logic.

Follow-up routing logic:
1. Check: has the patient messaged in the last 24 hours?
2. If yes → send free-form message
3. If no → check if a template message is approved for this follow-up type
4. If template available → send template
5. If no template → skip this follow-up, log as blocked
